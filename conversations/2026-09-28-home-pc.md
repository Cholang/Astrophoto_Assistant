## 7. 기술 선택 (Claude ↔ GPT)
- **Claude 처음 안**: Electron + 웹 UI (기존 Node 스크립트 재사용, 화면 만들기 쉬움, 원격 확인에 유리)
- **GPT 첫 의견 요지**: 웹 기술로 만들어도 브라우저 느낌은 아님. 다만 몇 년 켜 둘 Windows 장비 프로그램이고 NINA가 C#/WPF이며 플러그인도 C#이니 C# + WPF/Avalonia 추천. UI와 NINA 통신 분리, 내부 상태 머신 구조 제안.
- **Claude 응답**: 구조 제안과 플러그인 경로는 동의. 안정성은 언어보다 설계 문제. 원격 확인(폰·태블릿)이 결정 기준.
- **사용자**: 촬영 PC에 메인 세팅, **텐트 안 폰에서 같이 보는 동기화**를 원함. 플러그인으로 넣는 건 구체적으로 어떤 경우인가?
- **Claude**: 플러그인 후보 = 시퀀스 안에서 판단할 안전·복구 로직 (구름 대기, HFR 악화 시 AF, 이슬점 열선, 박명 종료). 동기화 요구 → **UI는 웹, 코어는 서버**. 폰에서는 보기·중지만, 물리 동작 시작은 장비 옆에서만.
- **GPT 두 번째 의견 요지**: 원격 접속 이점은 Electron이 아니라 웹 UI + 서버 덕분. 플러그인 이분법도 과함. 제3안: **C#/.NET 코어(ASP.NET Core) + React/TypeScript 화면 + WPF+WebView2 창**. 코어 라이브러리를 데스크톱과 플러그인이 공유 가능. PC는 상세 화면, 폰은 축약 화면.
- **Claude 응답**: 두 지적 모두 인정. 남은 차이는 코어 언어뿐 → **GPT 최종안 채택**. 단, 플러그인 공유 코드는 의존성 없는 순수 로직으로 분리해야 함(NINA와 같은 .NET 버전·라이브러리 충돌 주의).

## 8. 쉬운 설명
- **사용자**: 프로그래밍 지식이 없어서 반 정도만 따라가겠다.
- **Claude**: 식당 비유로 설명 — NINA=주방 기계, 코어 서버=주방장(한 명, 촬영 PC), 화면=메뉴판(노트북·폰 공용), 데스크톱 창=건물, 폰=배달. 언어 선택은 코드 작성에 필요한 결정이고, 사용자는 "어떤 화면이 어떤 순서로"를 판단하면 됨.
