## 1. 유지할 사용자 의도와 현재 초안

- AI와 대화하며 대상 → 구도 → 촬영 설정 → 끝난 뒤를 정한다. 현재 네 카드 구조를 전제로 검토하며 다시 만들라는 요청이 아니다.
- 과거 기록을 계획에 참고하고, 후보를 비교한 뒤 목표를 확정한다. 실행 전 계획에서 노출·필터·분량/종료 조건을 확인한다.
- 후보를 실제로 이동해서 비교하는 정책을 채택한다면, 대화 중 `이 후보로 이동할까요? [승인]`으로 충분하다. 별도 승인 화면·플로우 도형을 추가하라는 요구가 아니다.
- 기존 복구 흐름의 `주기적 재확인` 라벨과 사용자 중단 메모로 의도를 표현한다. 별도 대기 도형 추가는 사용자가 불필요하다고 판단했다.
- 필수 장비는 선택한 촬영 구성에 따라 판단하고, 사용하지 않는 장비는 검사에서 제외한다. 선택 장비 연결 실패는 경고하며 촬영 가능 여부는 준비 단계에서 판단한다.
- AA 경통 목록과 관측지 관리 등 앞부분의 기존 흐름을 유지한다. NINA 프로필을 모든 정보의 원본으로 되돌리라는 제안이 아니다.

현재 확인한 구현 기반:

- `web/src/screens/PlanScreen.tsx`: 대화·선택지, 오늘 밤 그래프, 네 카드, 카드 수정, 요약과 준비 시작 버튼.
- `src/Astro.Server/Assistant/PlanTools.cs`: 대상 검색·추천, 계획 변경 도구, 시간·장수 계산. AI 문장과 계획 값을 분리해 도구로 계획을 채우는 구조.
- `src/Astro.Server/Sky/Tonight.cs`: AA의 선택 경통을 우선하고 NINA 프로필에서 카메라·센서 정보를 읽어 예상 화각 계산.
- `src/Astro.Server/Assistant/PlanAssistant.cs`: 대화와 밤 컨텍스트 유지, 연습 대화 전환.
- `web/src/App.tsx`: 준비 단계는 안내용 placeholder. 실제 시퀀스 전달이 완성됐다고 전제하지 않는다.

## 2. 먼저 정리할 문서 간 정책 차이

### CX-PLAN-01 · 후보 비교에서 실제 이동을 허용하는가

**상태: 정책 확인 필요. 코드 결함으로 판정하지 않음.**

- 이 채팅의 기존 플로우는 후보 GoTo·프레이밍 비교와 이동 전 대화창 승인을 포함한다.
- 현재 `DESIGN.md`의 촬영 계획 절, `flow.mmd`의 CAND, `PlanScreen.tsx` 주석은 모두 **계획 화면에서 적도의를 움직이지 않고 미리보기만 제공**한다고 명시한다.
- 구현과 현재 저장소 문서는 이 점에서 일치한다. 과거 대화만 근거로 승인 버튼이나 실제 슬루를 임의로 추가하지 않는다.

**Claude 요청:** 최신 제품 결정의 맥락을 확인하고, 미리보기 전용 유지인지 승인 후 후보 이동까지 제공할지 차이를 설명한다. 명확한 후속 결정이 없으면 사용자에게 이 한 가지를 확인한다. 어느 쪽이든 문서와 목업의 표현을 일치시킨다.

**수용 기준:** 미리보기가 실제 장비 이동으로 오해되지 않는다. 실제 이동을 선택한 경우 사용자 승인 전 명령이 실행되지 않는다.

## 3. 계획 → 준비 연결 전에 검토할 설계 항목

아래는 초안의 현재 표현을 실제 실행 계획으로 확장할 때의 검토 항목이다. 심각도별 버그 판정이나 전체 구현 지시가 아니다. 각 항목의 세부 정책은 제안이며, 채택 여부를 기록한다.

### CX-PLAN-02 · 회전 미확인과 0도 회전을 구분

**근거:** `PlanTools.cs`의 `set_framing` 스키마는 “모르면 0”, `SetFraming`은 누락 시 0을 넣는다. `Plan.cs`의 `PlanFraming.RotationDegrees`는 필수 숫자이며 화면은 이를 `0°`로 표시한다.

**영향:** 현재는 표시용 초안이지만 이 숫자를 회전 명령으로 바로 전달하면 “현재 방향 유지/모름”이 “0도로 회전”으로 바뀔 수 있다.

**검토 방향:** 현재 방향 유지·각도 지정·미확인을 구분한다. 대상 좌표와 촬영 중심 좌표도 구분할 수 있도록 계획한다. 로테이터 없이 중심을 옮기는 구도와 카메라 회전은 별개다. `FovPreview`의 문구 기반 좌우 이동과 타원은 개념 미리보기이며 솔빙된 실제 구도라고 표시하지 않는다.

**시뮬레이션 확인:** 회전 요청이 없는 대화에서 0도 회전을 생성하지 않음. 로테이터가 없어도 중심 배치 의도는 보존. 실제 좌표 변환·솔빙은 후속 준비 단계 과제로 분리.

### CX-PLAN-03 · 장비에 맞는 질문과 설정

**근거:** `Tonight.cs`의 `Rig`에는 필터휠·가이더 유무가 있고, `PlanTools.Guiding`은 “없이 진행”을 반영한다. 반면 `PlanSettings`와 화면 감도는 ISO 중심이며, `Recommend`는 기본 ISO 800 등의 단순 표다. AI 프롬프트와 `ScriptedChatModel`에는 고정 필터 선택지가 있다. `SetAfter`는 장비 능력 인자를 받지 않는다.

**영향:** 특정 장비를 위한 초안은 유지할 수 있지만, 다양한 장비를 대상으로 할 때 미지원 자동 동작이나 보유하지 않은 필터가 실행 가능한 선택처럼 보일 수 있다.

**검토 방향:** 최초 지원 장비 범위를 먼저 명시한다. 자동 가능·수동 가능·사용 안 함·미확인을 필요한 만큼 구분하고, 필터휠 없음과 필터 없음, 의도적 미사용과 일시 연결 끊김을 동일하게 처리하지 않는다. Gain/Offset 카메라, 냉각·포커서·플랫·전원 제어는 지원 범위에 맞춰 확장한다. 연결 해제와 전원 차단도 구분한다.

**시뮬레이션 확인:** 장착 수동 필터 유지, 미지원 회전·냉각 등의 자동 명령 제외, 필요한 장비가 끊겨도 계획 기능을 조용히 삭제하지 않음. 모든 내용을 새 질문으로 늘리지 말고 기존 정보로 채운다.

### CX-PLAN-04 · 종료 조건과 예상 장수를 실행 의미로 보존

**근거:** `PlanSettings.EndCondition`은 화면용 문자열이며 `Recount`는 문장의 시작 부분으로 정책을 복원한다. 계산 시작은 대상 관측 가능 시각과 어두운 시간으로 정하며 현재 시각·사용자 시작 가능 시각은 해당 계산에 반영하지 않는다. 장당 부가 시간은 고정 6초다.

**검토 방향:** 종료 조건을 표시 문구와 별도 구조로 보존한다. 시간 제한과 장수 목표를 구분하고, 시간 제한에서 계산한 예상 장수를 필수 완료 목표로 바꾸지 않는다. 종료 시각이 촬영 종료인지 장비 정리 완료인지 정책을 정한다. 현 단순 추정식 자체는 초안 결함으로 취급하지 않되 UI와 실행 양쪽에서 추정값임을 유지한다.

**시뮬레이션 확인:** 자정 이후 종료 시각, 밤중에 계획 시작, 시작보다 이른 종료 시각, 관측 가능한 시간이 없는 대상. 실현 불가능한 시간 계획을 그대로 준비 완료로 표시하지 않음. 예상 장수 변화로 사용자의 종료 시각이 바뀌지 않음.

### CX-PLAN-05 · 네 카드 입력 완료와 실행 준비 완료를 구분

**근거:** `ShootingPlan.Complete`는 네 값의 null 여부만 검사한다. `PlanScreen.tsx`의 준비 시작 버튼은 이 값과 대화 중 여부를 기준으로 활성화한다. `SetTarget`은 기존 구도·설정을 비우는 대신 크기·시간을 재계산해 유지한다.

**영향:** 지금의 버튼은 placeholder로 이동하므로 실장비 오동작이 확인된 것은 아니다. 향후 실행을 붙일 때 “카드가 채워짐”을 “모든 값과 장비가 검증됨”으로 사용하면 안 된다.

**검토 방향:** 계획 입력 완료와 준비 단계에서 확인할 항목을 나눈다. 대상 변경 시 유지 가능한 값과 재확인이 필요한 값을 구분한다. 모든 카드를 무조건 초기화하라는 의미는 아니다.

**시뮬레이션 확인:** 네 카드가 찬 상태에서 대상 변경, 미확인 회전, 0장/유효하지 않은 시간 계획. 준비 단계로 넘기는 미확인 항목과 사용자 확정 내용을 명시하고, 준비 진입 자체와 실제 촬영 허가를 구분한다.

### CX-PLAN-06 · 관측지·장비 변경 시 계획 정보의 신선도

**근거:** `PlanAssistant.EnsureStartedAsync`는 같은 밤의 `_night`가 있으면 재사용한다. `TonightService`는 새로 읽을 때 AA 경통 값을 반영한다. 관측지 변경의 `SiteService`에는 `plan.Reset()` 호출이 있어 이미 처리 경로가 존재한다.

**검토 방향:** 이미 있는 관측지 reset을 중복 구현하지 않는다. 카메라·경통·프로필 변경과 NINA 재연결에서 계획 유지/재계산/재확인의 경계를 별도로 추적한다. 같은 구성으로 복구했을 때 대화 전체를 잃지 않게 한다. 이번 확인만으로 모든 변경 경로가 잘못됐다고 단정하지 않는다.

**시뮬레이션 확인:** 같은 밤에 광학 조합 변경 후 화각·추천 갱신, 관측지 변경 후 고도·시간 갱신, 같은 장비 재연결 후 사용자 의도 유지. 프로필 전환 시 다른 프로필의 계획 혼입 여부도 확인.

### CX-PLAN-07 · 준비 단계에 넘길 구조화된 계획

**근거:** 현재 `PlanTarget`은 카탈로그 Id를 보유하고, 구도는 배치 문구, 종료 동작은 표시 문자열 중심이다. 준비 화면은 미구현이다. `api-coverage.md`에는 템플릿·시퀀스 편집과 중단/재개의 후속 확인 과제가 있다.

**검토 방향:** 자연어 대화 → 구조화된 계획 → 지원 기능·시간 검증 → 준비 단계 → 검증된 시퀀스 템플릿 적용의 경계를 정한다. 카탈로그 Id를 좌표로 해석하는 주체, 촬영 중심·회전 의도, 노출/감도/필터, 시간 또는 분량 목표, 종료 동작과 수동 개입 항목을 전달할 수 있어야 한다. AI 문장이나 화면 문자열을 그대로 장비 명령으로 사용하지 않는다.

**시뮬레이션 확인:** 같은 확정 계획으로 일관된 준비 입력 생성, 미지원 자동 기능 제외, 명령 실패를 성공으로 표시하지 않음. 실제 API 필드·시퀀스 stop/start 복구는 후속 실기 검증으로 남기고 이번에 해결됐다고 기록하지 않는다.

1. HISTORY.md와 최신 diff를 읽고 이 문서의 기준 이후 변경을 확인한다. 줄 번호 대신 위 파일·함수명을 기준으로 현재 코드를 다시 찾는다.
2. CX-PLAN-01의 정책 차이를 먼저 정리한다. 과거 대화 또는 이 리뷰만으로 현재 제품 결정을 덮어쓰지 않는다.

4. 사용자에게 구현을 요청받은 범위만 수정한다. 이 문서 작성 승인을 전체 기능 구현 승인으로 해석하지 않는다.
5. 허용된 시뮬레이션·연습 대화로 확인하고, 실제 AI 호출로 한도를 소모하거나 실장비를 제어하는 검증은 별도 요청 없이 수행하지 않는다.
6. 변경·검증·남은 것을 HISTORY.md의 기존 규칙에 맞게 기록하고 이 문서에 처리 결과를 남긴다. Codex 재리뷰 결과는 Claude의 자체 확인과 구분한다.

## 6. 촬영 준비 화면 UI 리뷰 — 2026-10-01 · [Codex]

**상태: 아래 설계 방향에 사용자 동의. 리뷰 기록 요청에 따라 추가하며, 구현 완료나 구현 후 재검증을 뜻하지 않는다.**

- 기록 시 기준 HEAD: `01c6f32` (`docs: move reference and Codex documents into docs/, prepare screen content notes`).
- 검토 자료: [HISTORY.md](../../HISTORY.md), [DESIGN.md](../../DESIGN.md), [PREPARE_SCREEN_CONTENT.md](../PREPARE_SCREEN_CONTENT.md), `web/src/screens/PrepareScreen.tsx`, 준비 화면 CSS, `web/src/prepare.ts`.
- 범위: 극축 정렬 → 가이드 연결 → 대상 이동 → 초점 → 센터링 → 가이딩 → 테스트 촬영의 화면 구성과 사용자 상호작용.
- 검증: 문서와 코드의 정적 확인. 앱 실행·빌드·API 호출·실장비 검증은 하지 않았다. 의도된 시뮬레이션과 아직 없는 데이터 자체를 결함으로 판정하지 않는다.

### CX-PREP-UI-01 · 왼쪽 진행 목록과 오른쪽 작업 영역

설치 단계의 짧은 확인과 달리 준비 단계는 작업을 기다리고, 결과를 보고, 사용자가 개입하는 시간이 길다. 쉐브론 모양만 바꾸기보다 **왼쪽 세로 진행 목록 + 오른쪽 넓은 작업 영역**으로 구성한다.

- 일곱 단계는 유지한다. 왼쪽에는 단계명·상태·완료 결과 한 줄을 표시하고 현재 실행 단계를 강조한다.
- 오른쪽에는 현재 작업을 이해하고 판단하는 데 필요한 내용을 크게 배치한다. 제목·상태·주요 행동 위치는 단계가 바뀌어도 안정적으로 유지한다.
- 기존 상단 상태바와 하단 전체 단계 표시는 유지한다. 하단은 앱 전체 여정, 왼쪽은 준비 단계 내부 진행을 나타낸다.

**수용 기준:** 현재 진행 위치, 지금 하는 작업, 사용자가 해야 할 행동을 한 화면에서 구분할 수 있다.

### CX-PREP-UI-02 · 단계마다 판단에 필요한 결과를 주인공으로

현재 사진 영역은 `max-height: 22cqh` 등으로 보조 자료에 가깝다. 모든 단계를 같은 설명 카드에 넣기보다 단계별 핵심 자료에 충분한 공간을 준다.

| 단계 | 주된 작업 영역 | 함께 볼 정보 |
|---|---|---|
| 극축 정렬 | SharpCap에서 할 작업과 AA로 돌아오는 방법 | 외부 앱 상태, 사용자 정렬 완료 확인 |
| 가이드 연결 | 연결 진행 상태 | 시도 횟수, 실패 시 다음 행동 |
| 대상 이동 | 현재 방향과 목표의 관계 | 목표와의 거리, 고도, 이동 상태 |
| 초점 | 측정점이 쌓이는 초점 곡선 | 최근 별 사진, 측정 진행 상태 |
| 센터링 | 솔빙한 사진과 현재 중심·목표 표시 | 중심 오차, 보정 횟수 |
| 가이딩 | 가이드 그래프 | 선택한 별의 확대 이미지, 측정값과 판정 |
| 테스트 촬영 | 크게 보는 실제 테스트 사진 | 노출 정보, 확대·재촬영·촬영 시작 |

가이드 연결처럼 짧은 작업에 억지로 큰 그래픽을 만들 필요는 없다. 표의 실시간 자료와 이미지 표현은 실제 데이터 제공 가능 여부를 확인해 구현한다(CX-PREP-UI-06).

**수용 기준:** 사진·그래프를 읽어야 하는 단계에서 자료가 작은 부속물로 밀리지 않는다. 자료를 제공할 수 없는 상태도 솔직하게 표현한다.

### CX-PREP-UI-03 · 줄어드는 숫자보다 작업을 이해하는 핵심 수치

내용 문서의 “목표를 향해 줄어드는 숫자 하나”는 **“지금 작업을 이해하는 핵심 수치”**로 바꾸는 것이 적절하다. 초점 곡선은 측정 과정에서 오르내리고 가이드 오차도 흔들린다. 별 개수 역시 많아지는 것만으로 품질을 판정할 수 없다. 극축 정렬 안내나 재연결에는 목표 숫자가 없을 수 있다.

**수용 기준:** 진행 정도와 결과 품질을 구분한다. 수치가 계속 줄어야 정상이라는 인상을 주지 않으며, 의미 없는 진행률을 만들어 넣지 않는다.

### CX-PREP-UI-04 · 자동 진행·사용자 차례·실패를 명확히 구분

같은 화면 틀 안에서도 자동으로 진행 중인지, 사용자 판단을 기다리는지, 실패해 조치가 필요한지 분명해야 한다. 주요 버튼은 실제 행동을 설명한다. 예를 들어 가이딩 확인은 “좋아요”보다 “이 상태로 계속”, 테스트 사진 확인은 “촬영 시작”이 구체적이다. 이는 문구 방향의 예시이며 세부 문구를 모두 확정한 것은 아니다.

재시도는 왼쪽 상태 아이콘에 숨기지 않고 오른쪽의 일정한 행동 영역에 둔다.

**수용 기준:** 기다리면 되는 상태와 버튼을 눌러야 하는 상태가 혼동되지 않고, 실패한 작업의 재시도 위치를 쉽게 찾을 수 있다.

### CX-PREP-UI-05 · 지난 결과 보기와 다시 실행하기를 분리

왼쪽의 완료 단계를 선택하면 **결과만 조회**한다. 선택 자체가 장비 작업을 다시 실행해서는 안 된다. 다시 초점 맞추기 등의 재실행은 명시적인 별도 행동으로 둔다.

현재 `PrepareScreen.tsx`에는 `view.current` 변경 시 선택한 `picked`를 초기화하는 동작이 있다. 지난 결과를 보는 중에 자동 작업이 다음 단계로 넘어가더라도 화면을 강제로 빼앗지 않는 방향으로 조정한다. 대신 “현재 가이딩 진행 중 · 돌아가기”처럼 실행 중인 단계와 복귀 수단을 표시한다.

**수용 기준:** 조회 중인 단계와 실제 실행 중인 단계를 구분할 수 있고, 자동 진행이 과거 결과 조회를 끊지 않는다.

### CX-PREP-UI-06 · 데이터 제공 범위와 중단·복귀 동작을 먼저 구체화

선택한 가이드별 이미지, 센터링 중간 사진, 오토포커스 사진의 갱신 주기는 API에서 무엇을 받을 수 있는지 아직 확인이 필요하다. 원하는 화면과 현재 가능한 데이터를 구분해 설계한다.

- 최신 데이터, 마지막 수신 데이터와 시각, 아직 수신하지 못한 상태, 시뮬레이션을 구분한다.
- 실제 측정값이 없는데 별이나 망원경 방향이 실시간으로 움직이는 것처럼 꾸미지 않는다. 시뮬레이션 모드의 예시 사진·곡선은 시뮬레이션임을 표시해 사용할 수 있다.
- 준비 중단과 단순 화면 이동을 구분한다. 계획으로 돌아갈 때는 “중단 요청 → 중단 확인 → 계획 복귀”를 기본 방향으로 삼고, 단계별 중단 가능 여부와 서버 동작을 구체화한다. 이 동작이 이미 구현됐다고 가정하지 않는다.

**수용 기준:** 화면의 움직임이 실제 수신 상태와 일치한다. 계획 화면으로 돌아갔는데 작업이 계속되는지 사용자가 알 수 없는 상태를 만들지 않는다.

### CX-PREP-UI-07 · 대표 화면 세 개로 구성 검증

먼저 **극축 정렬·가이딩·테스트 촬영** 화면을 목업으로 비교한다. 각각 외부 앱에서 하는 수동 작업, 계속 들어오는 측정 데이터, 사진을 보고 확정하는 작업을 대표한다. 이 세 화면에서 공통 틀과 행동 위치가 자연스러운지 확인한 뒤 나머지 단계에 적용한다.

사진 확대 방식, 야간 모드의 사진 밝기 정책, 세부 배치와 데이터 갱신 주기까지 이번 합의로 확정한 것은 아니다. 대표 화면과 데이터 제공 범위를 확인하면서 구체화한다.

### CX-PREP-FLOW-01 · 캘리브레이션과 대상에서의 가이딩 분리

| 기본 순서 | 역할 |
|---|---|
| ① 극축 정렬 | SharpCap 정렬 → 가이드 카메라를 PHD2에 재연결 |
| ② 가이드 캘리브레이션 | 기존 값의 유효성 확인 → 필요 시 적절한 위치로 이동 → 가이드별 선택·캘리브레이션 |
| ③ 대상 이동 | 촬영 대상으로 슬루 |
| ④ 초점 | 주 카메라 초점 맞추기 |
| ⑤ 센터링 | 사진·솔빙·위치 보정으로 촬영 중심 맞추기 |
| ⑥ 가이딩 | 대상 부근의 가이드별 선택 → 가이딩 시작·안정화·오차 확인 |
| ⑦ 시험 사진 | 계획한 노출로 결과 확인 → 사용자가 본 촬영 시작 |

캘리브레이션은 보정 명령과 별의 이동 관계를 측정하는 작업이고, 가이딩은 그 값을 이용해 추적을 보정하는 작업이다. 캘리브레이션에 사용한 별을 촬영 대상까지 계속 따라가는 구조가 아니다.

PHD2는 천구 적도·자오선 근처에서 캘리브레이션하는 것을 권장한다. 촬영 대상 위치가 항상 적합하다고 가정하지 않는다. 적절한 위치의 선정과 실제 이동 명령 지원은 구현 시 확인하며, 위치를 바꿀 때 케이블·이동 한계 등 기존 이동 조건도 적용한다.

**수용 기준**
- 대상 위치에서 무조건 새 캘리브레이션을 실행하지 않는다.
- 캘리브레이션을 위해 이동했으면 이후 촬영 대상 이동·센터링을 거친다.
- 단계 종료는 사용자 버튼으로 다음 작업을 시작하는 최신 정책을 유지한다. 첫 이동이 ②에서 발생할 수 있으므로 이동 목적과 실행 버튼을 명확히 한다. ‘캘리브레이션 준비’는 문구 예시이며 정확한 버튼 문구는 화면에서 정한다.

- 가이딩에는 유효한 보정값이 필요하지만 반드시 그날 새로 만든 값일 필요는 없다.

- 가이딩을 사용하지 않는 계획에서는 ②와 ⑥을 모두 건너뛴다.

**수용 기준:** 같은 밤에도 장비 조건 변경을 무시하지 않고, 날짜가 바뀌었다는 이유만으로 항상 재실행하지 않는다. 단순 별 잃음과 보정값 무효를 구분한다.

### CX-PREP-FLOW-03 · 화면 순서와 필수 선행 조건을 분리

| 관계 | 성격 | 적용 기준 |
|---|---|---|
| 극축 정렬 → 캘리브레이션 | 현재 구성의 권장 순서 | 설치 상태를 먼저 확정하고, SharpCap이 쓰던 카메라를 PHD2에 넘긴다. 모든 정렬 방법에 통용되는 절대 순서로 해석하지 않는다 |
| 캘리브레이션 → 대상 이동 | 순서 변경 가능 | 대상으로 먼저 가도 되지만 캘리브레이션 위치까지 왕복할 수 있으므로 기본 순서는 유지 |
| 대상 이동 → 주 카메라 초점 | 순서 변경 가능 | 다른 별밭에서도 초점을 맞출 수 있다. 대상 근처에서 맞추는 것을 기본으로 둠 |
| 초점 → 센터링 | 조건부 | 솔빙 가능한 별상이면 센터링부터 가능. 초점 때문에 솔빙이 안 되면 초점 조정이 먼저 |
| 센터링 → 최종 가이딩 | 재작업을 줄이는 권장 순서 | 먼저 가이딩할 수도 있지만 센터링 이동 시 중지·재개·안정화가 필요할 수 있음 |
| 가이딩 → 최종 시험 사진 | 가이딩 사용 계획에서는 필요 | 본 촬영과 같은 추적 상태에서 확인. 그전에 찍는 짧은 초점·구도 확인 사진과 구분 |

**필수 조건은 ‘직전 단계 완료’보다 실제 상태로 표현한다.** 가이딩에는 유효한 캘리브레이션과 사용할 별이, 센터링에는 솔빙 가능한 사진이 필요하다. 최종 시험 사진은 확정된 초점·구도·추적·노출 조건에서 찍어야 한다.

별도 가이드 망원경을 사용하는 현재 구성에서는 주 카메라 초점과 가이드 캘리브레이션의 선후는 대체로 독립적이다. 단, 같은 적도의를 이동시키는 작업을 동시에 실행해도 된다는 뜻은 아니다.

### CX-PREP-FLOW-04 · 재시도는 영향을 받은 결과만 다시 확인

기본 안내는 ①→⑦로 유지해도 되지만, 뒤로 돌아갈 때 모든 작업을 처음부터 다시 시키지는 않는다. 다음은 구현 시 검토할 복구 경로다.

| 상황 | 제안하는 복구 경로 |
|---|---|
| 시험 사진에서 초점 불량 | 초점 재조정 → 필요 시 센터링 확인 → 가이딩 상태·안정 확인 → 시험 사진 |
| 구도 변경·센터링 재수행 | 가이딩 중지 → 센터링 → 별 선택·가이딩 재개·안정 확인 → 시험 사진 |
| 가이드별 잃음 | 원인 확인 → 별 재선택·가이딩 복구. 보정값이 유효하면 캘리브레이션은 유지 |
| 캘리브레이션 재수행 필요 | 가이딩 중지 → 적절한 위치에서 재수행 → 대상으로 복귀·센터링 → 가이딩 → 시험 사진 |

- 결과 조회와 작업 재실행은 구분한다. 과거 결과를 보는 것만으로 장비가 움직이지 않는다.
- 초점·구도·추적 조건을 바꾸면 이전 시험 사진은 과거 결과로 남기되, 새 상태의 확인 완료 근거로 사용하지 않는다.
- 재실행으로 영향을 받은 완료 상태는 재확인 필요로 바꾼다. 영향을 받지 않은 극축 정렬·유효한 캘리브레이션까지 일괄 초기화하지 않는다.
- 복구가 필요하다고 주 카메라 노출이나 적도의 이동과 충돌하는 장비 명령을 동시에 보내지 않는다. 중단 확인과 다음 명령의 경계를 서버에서 관리한다.

**시뮬레이션 수용 기준:** 정상 7단계, 기존 캘리브레이션 재사용, 가이딩 미사용, 별 잃음 후 복구, 시험 사진 후 재센터링, 캘리브레이션 위치로 재이동 후 대상 복귀를 확인한다. 명령 실패·미확인 상태를 성공이나 촬영 준비 완료로 표시하지 않는다.

### CX-PREP-IMPL-01 · 작업 취소와 실제 장비 정지 확인을 분리

계획 2.3에는 ③의 `StopMountAsync`가 있지만 ① RA 회전과 ② 캘리브레이션 위치 이동에도 공통 중단 규칙이 필요하다. `MoveAxis`는 시작 후 별도 정지 명령이 필요한 동작이므로 대기 작업의 취소만으로 정지했다고 처리하지 않는다.

**수용 기준:** 취소·시간 초과·예외 시 장비 정지를 시도하고, 정지 확인 전 다음 명령을 금지한다. 정지 확인 실패는 ‘중단 완료’가 아니라 ‘장비 상태 확인 필요’로 표현한다. 정지 요청이 일반 작업 대기열에 막히지 않도록 설계한다. 취소된 작업 토큰 때문에 정리용 정지 호출까지 생략되지 않게 한다. 프로세스 강제 종료·통신 단절 시 정지를 보장할 수 있다고 가정하지 않는다.

### CX-PREP-IMPL-02 · NINA·PHD2·직접 ASCOM 명령의 충돌 방지

직접 ASCOM 제어를 스위치·RA 회전으로 제한하는 범위에 동의한다. 다만 동시 연결 성공과 동시 명령의 안전성은 별개다. COM 전용 STA 스레드만으로 NINA·PHD2 경유 명령까지 직렬화되지는 않는다.

**수용 기준:** AA가 보내는 적도의 동작은 서버에서 한 작업에만 허용한다. RA 회전 중 슬루·보정 명령이 겹치지 않게 하고, 종료 후 정지·추적 상태를 확인해 제어를 넘긴다. 외부 앱에서 사용자가 직접 조작한 상태까지 AA의 잠금으로 통제된다고 가정하지 않는다.

### CX-PREP-IMPL-03 · 단위 미검증 값을 극축 정렬 성공 판정에 사용하지 않기

### CX-PREP-CODE-06 · [P2] 극축 정렬을 다시 해도 이전 캘리브레이션 재사용을 제안

**위치:** `src/Astro.Server/Prepare/Tasks/Calibration/CalibrationTask.cs:48`, `src/Astro.Server/Prepare/Flow/PrepareRunner.cs:305–315`.

**경로:** 같은 밤에 캘리브레이션 완료 → 새 계획으로 준비를 시작해 극축 정렬을 다시 수행 → 캘리브레이션. PrepResults는 초기화/무효화하지만 공유 Memory.LastCalibration은 그대로 남는다. 재사용 조건은 같은 밤 + 장비에 보정값 있음뿐이므로 새 극축 정렬 이전의 보정값도 재사용 후보가 된다.

### 코드 최적화·구조 개선 여지

1. **복구 경로 통합이 최우선.** 지금은 러너 StopCurrentAsync, SlewTask의 자체 멈춤, 예외 retry, RedoRequest가 서로 다른 경로다. CODE-01~03처럼 확인 규칙이 빠지기 쉽다. 작업의 재실행 요청은 선언적으로 받고 러너에서 정지·확인·무효화·실행 순서를 통일한다. 병렬 요청도 이 전환 경계에서 직렬화하되 정지 요청이 긴 일반 작업 뒤에 갇히지 않게 한다. 단순히 모든 메서드를 하나의 긴 lock으로 감싸는 해결은 피한다.

### CX-SHOOT-01 · P1 — 가이딩 정지를 확인하지 못해도 다음 대상·마무리로 진행한다

- **위치:** `src/Astro.Server/Shoot/ShootSession.cs:512` (`EndAsync`), `Shoot/RealShootDevices.cs:145–169`, `web/src/screens/ShootScreen.tsx:64–70`.
- `StopGuidingAsync`가 false를 반환하거나 예외가 나도 세션은 `Ended`가 된다. 화면은 정지 성공 여부 없이 `Ended`만 보고 예약된 마무리·대상 변경을 실행한다. 경고 문장은 다음 이동을 막지 않는다.
- 실제 어댑터도 NINA 정지 명령의 반환값을 버리고, PHD2 상태가 `Guiding`이 아니면 성공으로 처리한다. 이 조건에는 `LostLock`과 조회 실패도 들어간다. 별을 잃었거나 통신이 끊긴 것은 정지 확인과 다르며, 별이 돌아오면 다시 가이딩할 수 있다.
- **재현:** 가짜 장비가 정지에 false를 반환해도 `mode=Ended, reason=done, good=1`이었다. 실제 PHD2 상태별 분기는 정적 확인이며 장비에는 명령을 보내지 않았다.
- **수정 방향:** 정지 미확인을 별도 상태로 유지하고 재확인 전 다음 동작을 차단한다. 실제 어댑터는 명시적으로 정지된 상태를 확인해야 한다. 마무리 시작 서버 경로에도 같은 조건이 필요하다.
- **회귀 검증:** false·예외·LostLock·연결 끊김에서 다음 이동이 0회인지, 정지 재확인 후에만 다음 단계가 허용되는지 확인한다.

### CX-SHOOT-02 · P1 — 자오선 반전 자체가 실패해도 반전 완료로 기록하고 계속 촬영한다

- **위치:** `src/Astro.Server/Shoot/ShootSession.cs:217–224`, `Shoot/RealShootDevices.cs:186–203`.
- 실제 `FlipAsync`는 반전 명령 실패 또는 정지 확인 실패에서도 false를 반환한다. 세션은 이를 모두 센터링 실패로 해석하고 `_flipped=true`를 설정한 뒤 촬영한다. 이후에는 반전을 다시 시도하지 않는다.
- **영향:** 실제로 반전되지 않은 상태에서 자오선 이후 추적·노출이 계속될 수 있다. 장비별 한계 설정에 따라 위험이 달라지지만, AA의 반전 실패 처리 자체는 누락되어 있다.
- **재현:** 시간각 2°, 반전 false, 나머지 정상 응답으로 `flips=1, exposures=1, reason=done`이었다.
- **수정 방향:** 반전·센터링·가이딩 재개의 결과를 구분한다. 최소한 반전/정지 확인 실패는 촬영 재개를 막고, 반전 성공이 확인되어야 완료 플래그를 설정한다.
- **회귀 검증:** 각 구간 실패를 별도로 주입해 허용된 정책대로만 진행하는지 확인한다. 반전 실패 뒤 노출은 0회여야 한다.

### CX-SHOOT-03 · P1 — 홈·추적 끄기 실패 뒤에도 연결을 끊고 프로그램을 닫는다

- **위치:** `src/Astro.Server/Prepare/Tasks/Wrap/WrapTasks.cs:241–261`, `Prepare/Real/NinaRig.cs:221–232`, `web/src/screens/SummaryScreen.tsx:42–57`.
- `PackTask`는 `TrackingOffAsync`의 bool을 버린다. 홈 실패도 중단 조건이 아니므로 장비 연결 해제와 프로그램 종료를 계속한다. `CheckEndStateAsync`는 항상 Pass이고 AutoNext로 요약에 진입한다.
- 특히 홈 함수는 4분 동안 홈을 확인하지 못하면 false를 반환할 뿐, 이 반환이 이동 정지를 보장하지 않는다. 그러므로 홈 미확인 후 연결 해제는 아직 움직이는 장비의 제어 경로를 끊을 수 있다.

- **수정 방향:** 홈·이동 정지·추적 끄기의 확인 결과를 보존하고, 실패 시 재확인/복구 화면에 머문다. 확인 전 장비 연결 해제·프로그램 종료·전원 차단 안내를 진행하지 않는다.
- **회귀 검증:** 홈 시간 초과 및 추적 끄기 실패 각각에서 disconnect/close가 호출되지 않는지 확인한다.

### CX-SHOOT-04 · P1 — 이번 촬영의 저장 파일인지 확인하지 않아 이전 사진을 평가·이동할 수 있다

- **수정 방향:** 이번 촬영 시작 시각/가능하면 식별자로 저장 완료와 파일을 확인한 뒤 평가한다. 이전 기록 또는 저장 미확인은 제한된 재조회 후 실패로 처리하고 이전 파일을 이동하지 않는다.
- **회귀 검증:** 새 capture 완료 + 이전 image-history, 빈 history, 지연 후 새 history의 가짜 응답을 사용한다. 이전 파일 불변과 유효 장수 불증가를 확인한다.

### CX-SHOOT-06 · P1 — PHD2가 Guiding이면 적도의 추적 중단 판정을 덮어쓴다

- **위치:** `src/Astro.Server/Shoot/ShootSession.cs:318–333`, `Shoot/GuideWatch.cs`의 `Classify`.
- 분류 함수는 `MountTracking=false`를 `MountStopped`로 올바르게 판정한다. 그러나 호출자는 마지막에 `raw.Guiding ? None : loss`를 반환한다. 적도의 추적이 먼저 꺼지고 PHD2 상태가 아직 Guiding인 동안에는 추적 중단이 무시된다.
- **재현:** `Connected=true, Guiding=true, MountTracking=false`로 1장 노출 및 정상 완료가 발생했다. 실제 하드웨어 상태의 전환 지연을 전제로 하지 않아도 이 입력 조합의 분류 결과 소실은 재현된다.
- **수정 방향:** 적도의 중단·연결 끊김 같은 하드웨어 실패를 Guiding 상태보다 우선한다. 가이딩 중 약화 현상을 경고로만 처리하는 정책과 분리한다.
- **회귀 검증:** 분류 함수 단위 테스트뿐 아니라 해당 입력이 세션까지 전달됐을 때 노출 시작 차단/진행 노출 중단이 일어나는지 검증한다.

### CX-SHOOT-08 · P2 — 다크 촬영 실패를 무한 반복하고 복구 선택지를 주지 않는다

- **회귀 검증:** Capture가 항상 false인 가짜 장비로 호출 수가 제한되는지, Ask/중단 후 추가 촬영이 없는지 확인한다.

### CX-SHOOT-09 · P2 — 노출 중단 실패로 저장된 사진이 결과·제외 처리에서 빠진다

- **위치:** `src/Astro.Server/Shoot/ShootSession.cs:251–255, 373–400`.
- 노출 중 가이드 문제를 발견하면 `AbortExposureAsync` 결과를 무시한 채 촬영 task를 기다린다. 중단에 실패해 실제 사진이 저장되어 반환되어도 lost 분기는 shot의 파일을 처리하지 않고 복구 또는 종료로 넘어간다.
- **재현:** 노출 시작 후 적도의 중단 입력, abort=false, 늦게 성공한 촬영 결과/가짜 저장 경로를 반환했다. 결과는 `reason=mount, good=0, excluded=0`이고 해당 사진의 제외 처리도 호출되지 않았다. 실제 파일은 만들거나 옮기지 않았다.
- **영향:** 품질 문제로 버리려던 사진이 일반 폴더에 남고 촬영·제외 집계에서도 사라진다. 이후 원본 폴더를 스태킹할 때 섞일 수 있다.
- **수정 방향:** 중단 성공 여부와 최종 저장 결과를 모두 회수한다. 문제가 발생한 노출이 저장되었으면 제외 대상으로 기록·처리하고, 중단/파일 이동 실패도 별도 상태로 보존한다.
- **회귀 검증:** abort 성공/실패와 저장 유무의 조합, 중단 직전 저장 완료 경쟁 조건을 검사한다.

### 요청한 나머지 검토 범위와 최적화 의견

- **단계 재구성:** `PrepareFlow`의 공유 결과·두 러너 전환·ForeignRedo/Suspend, 초점 확인 및 AutoNext 변경을 기존 준비 계약과 대조했다. 이번 확인에서 위 항목과 별도로 확정할 중대 결함은 찾지 못했다. 준비 완료 상태와 실제 장비 상태가 같다는 보장은 별도 실기 검증 대상이다.
- **다크 Ask 취소:** 정상 경로에서는 촬영 완료 후 해당 Ask를 취소·회수하고, ‘여기까지만’을 누르면 진행 중인 노출 결과를 기다리는 구조다. 기존 관련 테스트도 통과했다. 다만 촬영/클릭이 동시에 완료되는 경계와 전체 중단·재진입은 추가 경쟁 조건 테스트가 필요하며, 모든 경우의 정합성을 보장했다는 뜻은 아니다.

### CX-APP-R1 · P1 — 홈 실패 뒤 정지 확인에 실패해도 홈 이동을 다시 명령한다

**위치:** `src/Astro.Server/Prepare/Tasks/Wrap/WrapTasks.cs:269–284`.

`PackTask`가 Home=false를 받으면 StopAsync를 호출하지만 그 bool을 사용하지 않는다. Stop=false여도 ‘다시 시도’를 누르면 루프 처음에서 HomeAsync를 다시 호출한다. 홈 명령 시간 초과는 이동 정지를 의미하지 않으므로, 이전 이동이 남아 있을 수 있는 상태에서 새 이동을 요청한다. 현재 안내도 정지 확인 없이 멈췄다고 표현한다. 이는 문구 문제가 아니라 다음 명령을 허용하는 조건 문제다.

**독립 재현:** 첫 Home=false, Stop=false, TrackingOff=true, 사용자 응답 retry로 구성했다. 호출 순서는 `Home → Stop(false) → TrackingOff → Home → TrackingOff → Disconnect → Close`였다. 두 번째 Home=true이면 최종 SafeToPowerOff도 true가 된다. 실제 장비는 사용하지 않았다.

**권고:** 정지 성공과 홈 성공을 분리한다. 정지 미확인 상태에서는 재확인 동작을 먼저 수행하고, 확인 전에는 Home을 다시 명령하지 않는다. 사용자가 직접 확인하는 선택은 기존 의도대로 유지하되 자동 확인과 구분해 기록한다. `Stop=false → retry → Home 0회`를 회귀 테스트에 추가한다.

### CX-APP-R2 · P2 — 제외 폴더 이동 실패를 성공으로 표시한다

**위치:** `src/Astro.Server/Shoot/ShootSession.cs:292–312, 528–536`, `Shoot/RealShootDevices.cs:228–243`.

실제 파일 어댑터는 파일 잠금·권한 문제·동명 파일 등으로 이동하지 못하면 null을 반환한다. 일반 F 처리와 새 `ExcludeFrame` 모두 이 실패를 사용자 상태에 반영하지 않고 ‘제외 폴더로 옮겼어요’라고 표시한다. 등급 F 자체는 유지하는 것이 맞지만, 원본 폴더에서 파일을 분리했다는 보장은 성립하지 않는다.

**독립 재현:** 첫 사진은 F, MoveToExcluded=null, 다음 사진은 정상으로 반환했다. `good=1, excluded=1, moves=1, reason=done`으로 끝나며 별도 이동 실패 상태가 없다. 실제 파일은 만들거나 이동하지 않았다. 성공 안내 분기는 코드로 확인했다.

**권고:** 품질 등급과 파일 이동 상태를 별도로 기록한다. 이동 실패 파일 목록·재시도 또는 수동 제외 안내를 요약에 남기고, 성공했을 때만 이동 완료로 표시한다. 사진 삭제나 덮어쓰기로 해결하지 않는다. null·예외·동명 파일 조건을 검증한다.

### CX-APP-R3 · P2 — 무가이드 촬영은 되지만 실제 자오선 반전에서 다시 가이더를 요구한다

**위치:** `src/Astro.Server/Shoot/ShootSession.cs:228–242, 339–347`, `Shoot/RealShootDevices.cs:97–109, 203–218`.

세션은 HasGuider=false의 일반 감시 결과를 건너뛰지만 반전은 항상 호출한다. 실제 `FlipAsync`는 ctx.HasGuider와 무관하게 PHD2 정지 확인을 먼저 요구하고, 끝에도 가이딩을 다시 시작한다. 가이더/PHD2 없이 준비를 통과한 구성은 반전 시점에 Flipped=false로 종료된다. 이번 무가이드 테스트는 실제 어댑터의 이 분기를 검증하지 않는다.

일반 촬영에서도 먼저 `GuideRawAsync`를 호출하고 나서 무가이드 여부를 판단하므로, 실제 어댑터는 불필요한 PHD2 연결·이벤트 수신을 시도한다. PHD2가 없으면 조회 지연이 매번 추가될 수 있다.

**권고:** 적도의 상태 조회를 가이더 조회와 분리하고, 반전 어댑터의 정지/재개도 HasGuider 조건을 따른다. 무가이드 반전에서는 mount/center만 호출하고 PHD2 명령이 0회인지 검증한다. 이 항목의 실제 어댑터 경로는 정적 확인이다.

### CX-APP-R4 · P2 — 촬영·마무리 중 NINA 재시작 경로가 해당 작업으로 복귀하지 않는다

**위치:** `web/src/App.tsx:48, 211–231`, `Prepare/Tasks/Wrap/WrapDevices.cs`의 `CloseProgramsAsync`.

NINA 감시 대상에는 shoot/wrap이 추가됐지만 `restartNina`가 resumeTo를 기록하는 목록에는 두 단계가 없다. 이 상태에서 재시작하면 엔진·연결 이후 기본 경로인 출발 전 점검으로 돌아가며, 기존 촬영/마무리 세션을 정리하거나 복구하는 절차와 연결되지 않는다. 서버의 작업 상태는 화면 이동만으로 취소되지 않는다.

또한 PackTask가 정상적으로 NINA를 닫는 동안에도 wrap은 감시 대상이다. 종료 이벤트가 요약 전환보다 먼저 오면 정상 종료를 장애 팝업으로 표시할 수 있다. 팝업 노출 시간은 실행 타이밍에 따라 달라지며 이번에는 UI 실기로 측정하지 않았다.

**권고:** 정상 종료 예정 상태를 서버에서 전달해 해당 경고를 억제한다. 예기치 않은 종료는 실행을 정리·장비 재확인한 뒤 원래 작업의 복구 화면으로 돌아가게 한다. 단순히 resumeTo에 문자열 두 개를 넣고 자동 재개하면 충분하지 않다. 사진 노출 중 끊김·다크 중 끊김·정상 Pack 종료를 각각 확인한다.

### CX-APP-R5 · P2 — 실제 시험 사진의 ‘9칸 확대 보기’가 모의 그림으로 바뀐다

**권고:** 실제 이미지의 9개 영역을 잘라 보여 주거나, 구현 전에는 실제 모드에서 이 선택을 비활성화하고 미지원 상태를 분명히 한다. 이미지 식별자를 고정한 테스트 사진으로 아홉 영역이 동일 사진에서 왔는지 검증한다. 이번에는 렌더 분기·버튼 노출·그림 생성 코드를 대조했으며 실제 카메라는 사용하지 않았다.

### CX-NIGHT-01 · P1 — 반전 완료 판정이 방향 미확인과 이동 중 상태를 통과시킨다

### CX-NIGHT-04 · P1 — 환경 센서 COM 조회가 멈추면 촬영과 가이드 감시도 멈춘다

### CX-NIGHT-05 · P1 — 파일 검색이 실제 새 사진을 놓치고 같은 이름의 이전 사진을 반환할 수 있다

**상황·근거:** 시작 위치로 이동 중 응답이 끊기거나 시간 초과가 난 뒤 새로 추가된 수동 진행을 선택한다. MoveFocuserAsync 실패는 물리적 정지 확인이 아니지만 ManualDone으로 완료 결과를 만들고, CheckEndStateAsync는 Manual=true이면 장비 상태를 읽지 않고 통과한다. 포커서가 계속 움직이거나 상태를 모르는 채 준비 완료·다음 작업으로 갈 수 있다. 초점 품질을 사용자가 받아들이는 선택과 모터 정지 확인은 별개다.

**모의 재현:** MoveAsync=false, 실제 상태는 Moving=true인 가짜 포커서로 실제 FocusTask/PrepareRunner를 실행했다. 수동 선택 후 **작업 Done, Stop 호출 0회, 끝 상태 조회 0회**였다.

**고칠 방향:** 자동 위치/곡선 품질 검사는 생략하더라도, 자동 포커서가 연결된 상태에서 실패 후 넘어갈 때는 취소·정지 확인을 남긴다. 정지 미확인이면 기존 장비 상태 재확인으로 보낸다. 애초에 포커서가 없는 순수 수동 구성과 구분한다.

### CX-20-05 · P2 — 포커서 위치 조회 실패가 0점 복귀 완료 기록으로 저장된다

**파일:줄:** `src/Astro.Server/Prepare/FocuserPark.cs:77–85, 99–103`, `src/Astro.Server/Prepare/Real/RealFocusDevices.cs:89`.

**상황·근거:** ConnectedAsync는 성공했으나 다음 위치 조회부터 통신이 실패한다. PositionAsync의 `?? 0` 때문에 park는 이미 0이라고 판단해 이동을 생략하고, 두 번째 조회도 0으로 받아 완료 기록을 남긴다. ReadyAsync에도 같은 조합이 있어 다음 점검의 0점 확인을 잘못 생략할 수 있다. 기존 위치 조회의 기본값을 새 “복귀 완료 증거”로 사용하면서 생긴 문제다.

**고칠 방향:** 위치를 nullable 또는 성공 여부가 있는 상태로 반환하고, 유효한 Connected=true·Position=0·Moving=false 관측으로만 기록/Ready를 인정한다. 확인 불가나 복귀 실패 때 이전 완료 기록을 계속 신뢰하지 않도록 처리한다.

### CX-20-06 · P2 — 앱이 켠 프로그램만 닫는다는 조건이 프로세스별로 적용되지 않는다

**파일:줄:** `src/Astro.Server/Engine/ProgramCloser.cs:14–16, 27–35, 45–63`, `src/Astro.Server/AppServer.cs:158–159`.

**상황·근거:** 사용자가 PHD2 또는 SharpCap을 먼저 실행해 둔 뒤 아이라가 N.I.N.A.만 새로 실행한다. 앱 종료는 LaunchedNina 하나로 허용되고, CloseAsync는 이름이 같은 **모든** PHD2·SharpCap을 닫는다. Empire 역시 “아이라 시작 이후 실행됨”만으로 소유를 단정해, 사용자가 나중에 직접 켠 Empire/ASCOM 서버도 종료하거나 Kill할 수 있다. 시작 시각의 선후관계는 실행 주체의 증거가 아니다.

**검증:** 프로세스 선택 조건과 실행 플래그 설정 코드 확인. 실제 프로세스 열기·닫기·Kill은 수행하지 않았다. 마무리 PackTask가 사용자가 켠 프로그램도 닫는다는 기존 정책과, 일반 앱 종료에서 소유 프로그램만 닫는 정책을 구분한 지적이다.

**고칠 방향:** 직접 실행한 PID와 시작 시각을 보관하고, 간접 실행은 실행 전후 집합 등 확인 가능한 근거로 추적한다. 일반 앱 종료와 장비 정리의 종료 정책을 분리한다. 소유가 불명확한 프로그램은 자동 강제 종료 대상에서 제외한다.

### CX-20-07 · P2 — USB 존재와 끊어진 배선을 근거로 정상 전원 배선을 영구 수정한다

**파일:줄:** `src/Astro.Server/Engine/EquipmentConnector.cs:148–153, 283–285`, `src/Astro.Server/Profiles/PowerWiring.cs:88–98`.

**상황·근거:** 실제 배선이 DC → 적도의 → 파워박스인데 새들 출력이 꺼져 있거나 그 사이 케이블만 빠져 있다. 적도의는 연결되고 파워박스는 0V일 수 있으므로, 이 상황은 정상 배선 설정과 모순되지 않는다. 그런데 코드는 파워박스 전원을 DC 직결로 Learn해 프로필을 덮어쓴다. 이후 안내가 원래 새들 출력/케이블 대신 잘못된 배선을 믿는다.

PoweredAnywayAsync도 USB/COM 존재를 관측한 직후, 실제 장비 연결 성공 전부터 Learn한다. USB 회로만 살아 있고 별도 구동 전원이 없는 상태나 동일 제조사 USB 장치가 보이는 상태를 해당 장비의 전원 공급원으로 확정할 수 없다.

**검증:** 분기 조건과 영구 저장 경로를 대조했다. 실제 배선·전압은 조회하지 않았다. 조용히 학습한다는 합의 자체가 아니라 **관측으로 결론을 확정할 수 없는 조건**을 문제로 본다.

**고칠 방향:** 일시적인 연결 시도 허용과 영구 배선 변경을 분리한다. 0V·USB 존재만으로 Learn하지 말고, 공급 경로가 실제로 검증된 증거가 있을 때만 저장한다. 케이블 단선/출력 OFF는 기존 배선에서 가능한 고장으로 처리한다. 카메라 출력이 이미 ON이었던 경우도 “방금 켜서 나타남”의 증거와 구분한다.

### CX-20-08 · P2 — “가이딩 없이 진행”에서 PHD2 정지 확인 실패가 완료로 바뀐다

**파일:줄:** `src/Astro.Server/Prepare/Tasks/Calibration/CalibrationTask.cs:113–118, 180–185`, `src/Astro.Server/Prepare/Real/RealCalibrationDevices.cs:104–116`.

**상황·근거:** PHD2가 가이딩/캘리브레이션 중인데 stop_capture 또는 상태 조회가 실패하고, 사용자가 무가이드를 선택한다. NoGuideAsync는 StopAsync의 false를 버리고 Skipped 결과를 만든다. 이후 끝 상태 검사는 있으나, 실장비 어댑터가 PHD2 조회 실패를 빈 문자열로 바꾸므로 Guiding=false·Looping=false가 된다. 적도의가 슬루 중이 아니면 건너뜀 검사에 통과한다. PHD2가 실제로 멈췄는지 모르는 상태에서 이후에는 GuiderSkipped로 감시도 생략하게 된다.

**검증:** 실패 반환 → 결과 기록 → 실장비 끝 상태 변환 → 건너뜀 검사 경로의 정적 확인. PHD2 통신 단절은 실제로 일으키지 않았다. 정상 응답에서 PHD2가 가이딩 중이라고 알려 주면 기존 끝 상태 검사가 막는다는 점도 확인했다.

**고칠 방향:** StopAsync=false를 장비 재확인으로 연결하고, PHD2 상태 모름을 Stopped와 구분한다. 정지 확인 이후 GuiderSkipped를 확정한다. 무가이드 선택 시 대상 위치로 이동하지 않는 현재 동작은 유지한다.

### CX-20-09 · P2 — 임시 건너뛰기 중 정지 재확인에 성공해도 진행 버튼이 복구되지 않는다

**파일:줄:** `src/Astro.Server/Prepare/Flow/PrepareRunner.cs:641–647, 689–731`.

**상황·근거:** 극축 정렬/캘리브레이션의 임시 건너뛰기를 누르고 첫 정지 확인이 실패한다. TempSkipAsync가 StopCurrentAsync에 넘기는 후속 동작은 `() => Task.CompletedTask`다. 이후 “장비 상태 다시 확인”이 성공하면 RecheckStopAsync가 버튼을 비우고 이 빈 후속 동작만 실행한다. 건너뜀 결과·Done 상태·다음 버튼을 만드는 본문으로 돌아오지 않는다. 작업 상태는 Failed여서 Running/Waiting 때만 표시하는 임시 버튼도 사라진다.

**모의 재현:** 실제 PrepareRunner + 취소 가능한 FakeTask에서 첫 Stop=false, 재확인 Stop=true를 주었다. **상태 Failed, 액션 0개, ActiveTaskTitle=null**이 남았다. 정상 진행 버튼으로 복구할 수 없고 다른 재진입/다시 하기 경로가 필요해진다.

**고칠 방향:** 정지 확인 후 실행할 건너뛰기 완료 처리를 별도 함수로 두고, 최초 성공과 재확인 성공에서 동일하게 호출한다. 실패 중에는 Failed/정지 미확인 상태를 유지하되, 성공하면 결과·상태·다음 버튼을 한 번에 복구한다.

### CX-20-10 · P2 — 다른 알림이 있었다는 이유로 해석 못 한 경고까지 영구 숨김 처리된다

**파일:줄:** `src/Astro.Server/Engine/NinaNotices.cs:33–43, 334–350`.

**상황·근거:** 해석 가능한 알림과 규칙 밖 WARNING이 가까운 시각에 들어와 같은 NotificationsWindow에 쌓인다. 숨긴 뒤 5초가 지나면 전역 LastAddedAt만 검사하므로, 앞의 다른 알림을 추가했다는 이유로 AddFallback을 호출하지 않는다. 창은 이미 숨겨졌고 다시 표시하지 않는다. LastUnknown도 한 건뿐이라 여러 경고의 원문을 보존하지 못한다. “아이라가 알림 하나를 만들었다”는 사실이 “숨긴 알림 전부를 전달했다”는 보장이 아니다.

**모의 확인:** NinaNotices에 known 알림과 unknown warning을 넣고 Hider의 동일 시각 조건을 평가했을 때, 전달 목록에는 known만 남고 unknown은 fallback되지 않았다. 이 시험은 데이터·조건 검증이며 실제 Windows 토스트 숨김을 실행한 것은 아니다.

**고칠 방향:** 해석 못 한 경고를 큐에 보관하고 개별 전달 여부로 fallback을 처리한다. 다른 알림의 LastAddedAt을 전달 증거로 쓰지 않는다. 로그를 못 읽는 상태도 단순 안내 알림이라고 확정하지 않는다. 원래 창을 다시 띄우지 않는 정책을 유지하더라도 아이라 내부에 누락 없는 일반 알림 경로가 필요하다.

### CX-20-11 · P2 — 시작 로고 외의 새 사용자 창도 항상 위 속성을 잃을 수 있다

**파일:줄:** `src/Astro.Server/Engine/BackgroundWindows.cs:69–75, 87–105, 120–123, 137–151`.

**상황·근거:** 연결 감시가 켜져 있는 동안 사용자가 마우스로 N.I.N.A./Empire/PHD2의 새 항상 위 창을 열거나, 전에는 숨겨져 있던 창을 표시한다. before에는 감시 시작 때 보이던 창만 들어 있고, 대상은 PID/프로세스 이름과 topmost 여부로 결정한다. 새 창이 실제 시작 로고인지, 사용자 대화창인지는 구분하지 않는다. Alt/Windows 키를 쓰지 않은 사용자 전환은 감지하지 못해 해당 창의 topmost를 제거하고 포커스를 가져올 수 있다. Release도 아이라의 topmost만 해제하며 상대 창 속성은 복구하지 않는다.

**검증:** 창 선택·속성 변경·해제 코드를 확인했다. 실제 사용자 창을 열거나 topmost 속성을 바꾸지는 않았다. 감시 전에 이미 보이던 창과 대상 프로세스 밖의 창은 제외하는 보호는 있다. 따라서 모든 창을 잘못 건드린다는 지적은 아니다.

**고칠 방향:** 확인된 시작 로고의 제목/클래스·소유 관계 등으로 범위를 좁히고, 사용자 입력으로 활성화된 창은 제외한다. 임시 속성 변경이 꼭 필요하면 HWND/PID와 원래 값을 보관해 감시 종료 시 유효성을 확인하고 복구한다. 사용자 창·숨겼다 다시 연 창·실제 시작 로고를 모의 창으로 각각 검증한다.
