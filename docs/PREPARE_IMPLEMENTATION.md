## 0. 원칙 (바꾸지 않을 것)

- **서버가 상태를 갖고 화면은 그리기만** 한다 (지금 구조 유지). 화면을 다시 열어도 이어서.
- **장비 동작은 어댑터 뒤에** 둔다. 준비 흐름은 모의인지 실제인지 모른다 (지금 `IPrepareDevices` 유지·확장).
- **v1은 사용자 장비 기준**: Proxisky UMi17X(OnStepX) · ToupTek G3M662M(가이드) · Fujifilm X-T5(주) · Pleiades68(260mm F3.8) · Oasis Focuser Rose · WandererBox Plus V3 · N.I.N.A. 2.2 · PHD2 2.6.14 · SharpCap 4.1.
- **AI는 판정 고리 밖**: 등급·재시도·멈춤은 규칙이 정하고, AI는 설명 문구만.
- **실패는 AA가 먼저 처리**: 정해진 순서로 다시 시도하거나 대안으로 바꾸고, 끝내 안 될 때만 원인과 사용자가 할 일을 한 줄로.

## 2. 서버 구조

### 2.1 상태 모델 (화면에 보내는 것)

`PrepStepView`에 세 가지를 더한다. 화면은 이것만 보고 그린다.

```
PrepStepView
  + SubSteps: [{ id, label, status }]          // 위성. 없으면 빈 배열 (③⑤⑦은 없음)
  + Readout:  { label, big, kind, lines[] }    // 아래 읽기 자리 (예: "극축 오차 6.2′" / "아쉬워요" / 나사별 방향)
  + Live:     { kind, url?, data? }            // 하늘 화면: none | sharpcap | guideImage | skyMap | focusCurve | solvedPhoto | testPhoto
```

- `kind`는 등급 색 (ok / busy / warn / fail). 문구는 서버가 만든다 (화면에 문장 조립 없음).
- **실행 구분·시각·유효성 (IMPL-04)**: 단계를 (다시) 시작할 때마다 실행 번호 `RunId`를 새로 매기고, 장비·스크립트에서 온 값은 `RunId`가 지금 실행과 다르면 버린다. `Readout`·`Live`에는 측정 시각 `ObservedAt`과 상태(`fresh` / `stale` / `unverified`)를 붙여, 갱신이 끊긴 마지막 값을 정상 값처럼 보이지 않게 한다(예: 3초 넘게 안 오면 stale → 흐리게 + "값이 갱신되지 않습니다"). 숫자·단위·판정 근거는 문장과 별도 필드로 보존한다. 애니메이션이 끝난 것을 장비 작업 완료의 근거로 쓰지 않는다
- 이미지(창 캡처, 가이드 사진, 시험 사진)는 `/api/prepare/live/{id}`에서 받고 `Live.url`에 번호를 붙여 갱신을 알린다.

### 2.2 장비 어댑터

| 어댑터 | 경로 | 하는 일 | 상태 |
|---|---|---|---|
| `NinaApiClient` (확장) | N.I.N.A. Advanced API :1888 | slew(**RA는 도 단위**), home, tracking, focuser move·autofocus, camera capture, 솔빙·센터링(`slew?center=true`), guider connect·start·stop·info, profile 읽기 | 일부 있음 |
| `Phd2Client` (신규) | PHD2 JSON-RPC :4400 | 이벤트 스트림(AppState, Calibration*, GuideStep, StarLost, SettleDone), stop_capture → Stopped 기다림 → set_connected, loop, find_star, guide(recalibrate), get_calibration_data, set_exposure, save_image, get_pixel_scale | 시험 스크립트로 확인 |
| `SharpCapController` (신규) | 프로세스 + 스크립트 + 창 | `SharpCap.exe /camera "<이름>" /runscript aa_polar.py` 실행 → 스크립트가 노출·게인 설정, `SelectTransform("Polar Align")`, 1초마다 `{stage, active, x, y}`를 AA 서버로 POST, 필요할 때 `Advance()` → `CloseMainWindow`로 닫기. 창 캡처는 `PrintWindow(PW_RENDERFULLCONTENT)` + DPI 인식 | 실내 실기 확인 |
| `AscomDirect` (신규) | ASCOM COM (같은 장비에 N.I.N.A.와 동시 연결) | OnStep `MoveAxis`(RA만 회전), Wanderer `SetSwitch`/`GetSwitch`(**N.I.N.A. `switch/set`은 안 닿음**) | 실기 확인 |

- COM 객체는 STA 스레드 하나에서만 다룬다 (서버 전용 작업 큐). 창 캡처(`PrintWindow`, 동기 호출)는 장비 제어와 다른 스레드에서.
- **어댑터 계약**: 메서드마다 성공이 "명령 접수"인지 "실제 완료 확인"인지 명시하고, 취소·시간 초과 처리를 모든 메서드에서 같게 한다.
- **멈춤 (IMPL-01)**: 움직이는 동작(① RA 회전, ② 캘리브레이션 위치 이동, ③ 대상 이동, 포커서 이동)은 취소·시간 초과·예외 때 정지 명령을 보내고(`MoveAxis(0,0)`·`AbortSlew`·포커서 Halt), **정지를 확인하기 전엔 다음 명령을 보내지 않는다**. 정지 명령은 일반 작업 대기열을 거치지 않는 별도 경로로, 취소된 작업의 토큰과 무관하게 보낸다. 정지를 확인하지 못하면 "중단 완료"가 아니라 "장비 상태 확인 필요"로 표시한다. AA가 강제 종료되거나 통신이 끊긴 경우 정지를 보장한다고 가정하지 않는다(그때는 적도의 자체 한계·멈춤 감지에 맡김).
- **적도의 명령은 한 번에 하나 (IMPL-02)**: AA가 보내는 적도의 동작(N.I.N.A. slew·home, ASCOM `MoveAxis`, PHD2 캘리브레이션·가이딩 시작)은 서버의 적도의 잠금 하나를 잡은 작업만 보낸다. 끝나면 정지·추적 상태를 확인하고 잠금을 푼다. 가이딩 중 PHD2의 보정 펄스는 PHD2의 몫으로 두고, 그동안 AA는 적도의 동작을 보내지 않는다. 사용자가 다른 앱에서 직접 조작하는 것까지 이 잠금으로 막는다고 가정하지 않는다.
- SharpCap 스크립트가 보내는 HTTP는 localhost만 받고, 실행할 때 넣은 일회용 토큰으로 확인한다.

### 2.3 단계 분리 — 한 단계를 고쳐도 다른 단계가 그대로 동작하게 (2026-10-05 사용자 요청)

지금 코드는 `PrepareRunner` 한 클래스에 7단계 로직이 다 있고, 장비 인터페이스도 `IPrepareDevices` 하나에 모든 단계 메서드가 모여 있다. 이걸 아래처럼 나눈다.

**구조**

```
Prepare/
  Flow/        PrepareRunner      — 순서·끝 버튼·다시 하기 의존표·RunId·적도의 잠금·저장·SSE. 단계별 로직 없음
               IPrepStep          — 모든 단계가 지키는 계약
               PrepContext        — 계획(읽기 전용) + 앞 단계 결과(아래 결과 기록)
  Steps/       PolarStep · CalibrationStep · SlewStep · FocusStep · CenterStep · GuidingStep · TestShotStep
               (단계마다 폴더: 단계 클래스 + 그 단계 장비 인터페이스 + 판정 규칙 + 모의 장비 + 테스트)
  Devices/     NinaApiClient · Phd2Client · SharpCapController · AscomDirect — 여러 단계가 같이 쓰는 저수준 어댑터
```

- **`IPrepStep` 계약**: `Id` · `SubSteps` · `RunAsync(PrepContext, IStepReporter, CancellationToken)` → 결과 기록 · `OnAction(id)`(사용자 버튼) · `StopAsync()`(정지 확인까지). 단계는 화면 갱신을 `IStepReporter`(세부 과정·Readout·Live·버튼·상태)로만 하고, 다른 단계를 직접 부르거나 참조하지 않는다.
- **단계 사이는 결과 기록으로만**: 단계마다 끝나면 불변 기록을 하나 남긴다 — `PolarResult`(오차·시각) · `CalibrationResult`(유효 여부·직교 오차·시각) · `SlewResult`(도착 좌표) · `FocusResult`(위치·HFR·기온) · `CenterResult`(오차·카메라 방향) · `GuidingResult`(RMS) · `TestShotResult`. 뒤 단계는 앞 단계 **클래스가 아니라 이 기록만** 읽는다(예: ⑦은 `FocusResult.Hfr`와 비교). 기록의 모양을 바꾸지 않는 한 단계 안을 마음대로 고쳐도 다른 단계는 영향이 없다.
- **끝 상태 약속 (장비는 모든 단계가 공유하므로)**: 코드가 분리돼도 적도의·PHD2·카메라는 같이 쓴다. 단계마다 끝날 때 장비가 있어야 할 상태를 정해 두고(`EndState`), 러너가 실제 장비에서 읽어 확인한 뒤에만 다음 단계로 넘긴다. 어긋나면 그 단계 끝에서 바로 알린다("③이 끝났는데 추적이 꺼져 있습니다") — 한 단계를 고쳐 끝 상태가 달라져도 다음 단계에서 엉뚱하게 실패하지 않게.

  | 단계 | 끝 상태 약속 (러너가 확인) |
  |---|---|
  | ① 극축 정렬 | SharpCap 닫힘 · PHD2에 가이드 카메라 연결·루프 안 함 · N.I.N.A.–PHD2 연결 · 적도의 멈춤·추적 항성 · RA 회전 정지 확인 |
  | ② 캘리브레이션 | PHD2 보정값 있음(유효) · 가이딩·루프 안 함 · 적도의 멈춤·추적 켜짐 |
  | ③ 대상 이동 | 적도의 목표 2° 안 · 이동 멈춤 · 추적 켜짐 |
  | ④ 초점 | 포커서 멈춤 · 가장 좋은 위치에 있음 · 오류(멈춤 감지) 없음 |
  | ⑤ 센터링 | 목표 1′ 안 · 적도의 멈춤·추적 켜짐 · 카메라 노출 중 아님 |
  | ⑥ 가이딩 | PHD2 가이딩 중·안정(Settle 끝) · 별 잃음 없음 |
  | ⑦ 시험 사진 | 카메라 노출 중 아님 · 가이딩 유지 · 시험 사진 파일 저장됨 |

  단계 테스트에 "끝 상태 약속을 지키는지"를 넣고, 러너 테스트에는 "약속이 어긋나면 다음 단계로 안 넘어가는지"를 넣는다. 단계끼리 서로 부르지 않는다 — ⑥에서 "② 다시 하기"가 필요하면 러너에 제안만 하고, 러너가 의존표대로 처리한다.
- **장비 인터페이스는 단계마다 좁게**: `IPolarDevices`, `ICalibrationDevices`, `ISlewDevices` … 각 단계가 쓰는 메서드만(앞 표의 과정). 실제 구현은 공통 어댑터(`Devices/`)를 조합하고, 모의 구현도 단계마다 따로 — 한 단계의 모의를 바꿔도 다른 단계 테스트가 안 흔들린다. 예전 `IPrepareDevices` 하나짜리 설계는 버림.
- **러너는 단계를 모른다**: 러너는 `IPrepStep` 목록과 다시 하기 의존표(어느 결과가 바뀌면 어느 단계가 "다시 확인 필요"인지)만 갖는다. 단계 추가·순서 변경은 등록과 의존표만 고친다.
- **공통 규칙은 한 곳**: 멈춤 확인(IMPL-01), 적도의 잠금(IMPL-02), RunId·측정 시각(IMPL-04), 다시 하기 순서(IMPL-05)는 러너·`IStepReporter`·공통 어댑터에 두고 단계는 쓰기만 한다 — 단계마다 다시 구현하지 않음.
- **테스트로 보장**: ① 단계마다 자기 모의 장비로 단독 테스트(정상·실패 경우) ② 러너는 가짜 단계(정해진 결과를 내는 단계)로 순서·다시 하기·재시작 테스트 ③ 결과 기록의 모양을 고정하는 계약 테스트. ③을 고친 뒤 전체 테스트를 돌려 다른 단계·러너가 그대로인지 확인한다. 공통 부분(계약·결과 기록·공통 어댑터)을 고칠 때만 여러 단계가 영향받으며, 그때는 그 변경을 따로 리뷰한다.
- **화면도 같은 경계**: 단계마다 화면 조각 하나(`steps/PolarView.tsx` …)가 그 단계의 `Live`·`Readout`만 그린다. 원호·위성·패널·레일은 공통 껍데기. 서버의 단계 `Id`로 조각을 고른다.

### 2.4 단계 정의 (러너 등록·의존표 + 각 단계 클래스)
